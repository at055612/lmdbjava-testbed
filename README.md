# LmdbJava Test Bed

This is a test bed for evaluating the performance of [LmdbJava](https://github.com/lmdbjava/lmdbjava) on different file systems.

It currently has four different modes; `basic`, `write`, `read`, `all`.


## Basic Mode

This performs a very simple Hello World style test.
It is mainly to ensure LmdbJava/LMDB works at the most basic level on an environment.

1. Create a new LMDB Env.
1. Create a new LMDB DB.
1. Put a single entry.
1. Get the same entry, outputting the key/value.

### Usage:

```sh
export JAVA_OPTS="--add-opens java.base/java.nio=ALL-UNNAMED --add-opens java.base/sun.nio.ch=ALL-UNNAMED --enable-native-access=ALL-UNNAMED"
java ${JAVA_OPTS} -jar lmdbjava-0.8.2-testbed-all.jar basic
```

## Write Mode

This mode performs two sets of write operations, sequential and random.
Each set is timed.
A commit is performed at the end of each set.


### Sequential

N entires are written to the DB named `sequential`.
Entries are of the form:

`<sequential +ve 8 byte long>`: `<pseudo random +ve 8 byte long><padding>`

The padding is a random length between 10 and 1000 bytes in length to provide a variety of entry sizes.
The random number generator uses a fixed seed to ensure the test is repeatable.

The data is written in strict sequential key order and using `MDB_APPEND` mode for maximum write performance.
I.e. entries are written in the same order as they will be stored/iterated.


### Random

N entires are written to the DB named `random`.
Entries are of the form:

`<pseudo random +ve 8 byte long>`: `<pseudo random 8 byte long><padding>`

The padding is a random length between 10 and 1000 bytes in length to provide a variety of entry sizes.
The key is a random positive `long`.
The random number generator (RNG), in both cases, uses a fixed seed to ensure the test is repeatable.

The data is written in the order that keys are generated by the RNG, i.e. not in storage/iteration order.
This tests the performance of writes to random locations in the DB.

This mode is intended to either test just the write performance or to create a populated LMDB env for the _Read_ mode to use, i.e. if the LMDB env is on shared storage and the read is performed by a different host to the write.

### Usage:

```sh
export JAVA_OPTS="--add-opens java.base/java.nio=ALL-UNNAMED --add-opens java.base/sun.nio.ch=ALL-UNNAMED --enable-native-access=ALL-UNNAMED"
java ${JAVA_OPTS} -jar lmdbjava-0.8.2-testbed-all.jar write --rounds 5 --iterations 1000000 --dir /some/dir
```

* `rounds` - How many test rounds to perform.
  Each round consists of:
  * Deleting any existing environment.
  * Writing all sequential data.
  * Writing all random data.
* `iterations` - The number of entries to write in each set.
* `dir` - The directory to create the LMDB env in.
  It will be created if it doesn't exist.

Writing **cannot** be multi-threaded due to the way LMDB is designed.

_Write_ mode should be run in isolation, i.g. no other hosts/processing trying to run _Read_ mode.

Once the data is written it also writes the value of `iterations` to a DB named `meta` that can be read by _Read_ mode.


## Read Mode

This mode performs two sets of read operations, _sequential_ and _random_.
Each set is timed.
You do not set `iterations` as this will be determined by reading the `meta` DB.

The env for _Read_ mode uses the following env flags:

* `MDB_NOLOCK` - No locking is used to allow multiple hosts to concurrently read from a shared env.
* `MDB_RDONLY_ENV` - The env is opened in read-only mode.


### Sequential

A cursor is positioned at the first entry and it then iterates over every entry in the DB.


### Random

All entries in the DB are fetched by key, imitating random lookups.
Keys are fetched in the same order they were inserted, i.e. not the storage/iteration order.


### Usage:

```sh
export JAVA_OPTS="--add-opens java.base/java.nio=ALL-UNNAMED --add-opens java.base/sun.nio.ch=ALL-UNNAMED --enable-native-access=ALL-UNNAMED"
java ${JAVA_OPTS} -jar lmdbjava-0.8.2-testbed-all.jar read --rounds 5 --threads 2 --dir /some/dir
```

* `rounds` - How many test rounds to perform.
  Each round consists of:
  * Reading all data in the `sequential` DB sequentially.
  * Reading all data in the `random` DB using individual `get` calls.
* `threads` - How many threads to perform the two sets of read operations on.
  Each thread will perform exactly the same work.
* `dir` - The directory containing the LMDB env.

_Read_ mode can be run by multiple processes/hosts concurrently.


## All Mode

This mode essentially combines _Write_ and _read_ mode.

### Usage:

```sh
export JAVA_OPTS="--add-opens java.base/java.nio=ALL-UNNAMED --add-opens java.base/sun.nio.ch=ALL-UNNAMED --enable-native-access=ALL-UNNAMED"
java ${JAVA_OPTS} -jar lmdbjava-0.8.2-testbed-all.jar all --rounds 5 --iterations 1000000 --threads 2 --dir /some/dir
```

* `rounds` - How many test rounds to perform.
  Each round consists of:
  * Deleting any existing environment.
  * Writing all sequential data to the `sequential` DB .
  * Writing all random data to the `random` DB.
  * Reading all data in the `sequential` DB sequentially.
  * Reading all data in the `random` DB using individual `get` calls.
* `iterations` - The number of entries to write in each set.
* `threads` - How many threads to perform the two sets of read operations on.
  Each thread will perform exactly the same work.
* `dir` - The directory containing the LMDB env.


## System Properties

### Debug

Setting system property `testbed.debug` to `true` (default `false`) will enable additional debug logging.

```sh
export JAVA_OPTS="${JAVA_OPTS} -Dtestbed.debug=true"
```


### Check

Setting system property `testbed.check` to `false` (default `true`) will disable validation checks on the data being queried.
This validation adds an overhead, so it is best to run with checks to ensure it is functionally correct, then run without to capture performance timings.

```sh
export JAVA_OPTS="${JAVA_OPTS} -Dtestbed.check=false"
```


### System Requirements

LmdbJava Test Bed requires a Java 25 JVM to run.
`JAVA_HOME` should be set to the home of the Java 25 JVM and `java` should be on the path.
